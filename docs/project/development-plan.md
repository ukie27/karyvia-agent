# 后续开发计划

本文档记录尚未实施的后续开发事项。每项只描述背景、现状问题和目标需求，不预设具体实现方案；
后续确定开发时，再单独补充设计、边界和验证范围。

## 会话历史中的工具调用与结果重放

### 背景

Karyvia 在同一个 Turn 内已经能够保存并使用完整的工具调用过程：模型产生 assistant 的
`tool_calls`，Kernel 执行工具，将结果作为下一轮模型请求的一部分继续处理。

Pi 等 Agent 的会话模型会把 assistant 的工具调用和对应的工具结果作为结构化历史保存，并在
后续上下文组装时重放尚未被压缩的完整工具交换。较早的工具历史则可以通过压缩或裁剪控制上下文
大小。

### 当前问题

当前 Session 持久化记录只保存了工具结果及其 `tool_call_id`，没有保存产生这些结果的 assistant
工具调用声明。上下文重放时会跳过 `role=TOOL` 记录，因此工具调用过程只在当前 Turn 内有效，
后续 Turn 无法看到之前执行过的工具、调用参数及工具结果。

这种行为虽然避免了把孤立的工具结果重新交给模型，但也造成了会话历史与模型实际执行过程不完整：

- 模型无法在后续 Turn 中利用之前工具调用产生的上下文；
- 进程中断或下一轮继续时，模型可能无法判断某项操作是否已经执行；
- 文件、Shell、MCP 等工具的执行过程不能作为可重放的 Agent 历史；
- 并发工具的完成顺序与模型要求的调用顺序之间需要明确区分，否则历史可能无法被模型 API 接受。

### 需求

后续将会话历史调整为能够表达并重放结构化工具交换，满足以下要求：

1. Session 能够持久化 assistant 的工具调用声明，以及与其对应的工具结果。
2. 后续 Turn 组装上下文时，可以重放仍然有效的完整工具调用—结果对，而不是只重放工具结果。
3. 工具调用和结果必须保持合法的对应关系与模型要求的消息顺序，不能产生孤立或被拆开的工具交换。
4. 工具并发执行时，事件的完成顺序与写入模型上下文的调用顺序需要保持各自语义，不互相混淆。
5. 会话压缩和上下文压缩都必须把工具交换视为可验证的整体，不能在调用声明和结果之间推进错误的
   压缩水位。
6. 保留“完整 Session 历史”和“当前模型上下文投影”之间的区分；历史可以完整保存，但当前请求
   仍应通过压缩或裁剪控制上下文大小。
7. 这项改造需要明确新的持久化格式版本及旧 Session 数据的处理边界，不在没有决定前自行增加
   长期兼容逻辑。

本项只要求实现工具调用历史的结构化持久化与重放，不要求复制 Pi 的全部 Session 树、扩展消息
类型或供应商专属元数据设计。

## CLI 新建会话命令

### 背景

Karyvia 已经通过 `SessionKey` 区分不同会话。只要消息使用不同的
`conversation_id`，Session Store 就会加载一份新的会话历史；原有会话仍然可以继续保留和访问。
当前 CLI 也支持通过配置或嵌入式调用指定不同的 `conversation_id`，因此底层会话隔离能力已经存在。

### 当前问题

CLI 交互过程中会持续使用启动时配置的同一个 `conversation_id`，用户没有一个直接的交互命令来
开始一份新的会话。当前的 `/session` 只能查看当前会话状态，不能切换会话；如果用户想开始新会话，
需要修改配置并重新启动，交互体验不完整。

### 需求

后续增加 CLI 侧的新建会话能力，使用户可以在当前交互过程中主动开始一个新的会话，并满足以下要求：

1. 新会话应使用新的会话标识，后续输入不再加载旧会话的历史。
2. 原会话历史必须保留，不能把“新建会话”实现为无条件删除或清空原 Session。
3. 新建会话只影响后续输入，不应修改已经提交的消息及其所属 SessionKey。
4. 该能力首先面向 CLI 交互，不把 CLI 的会话切换行为强行扩展为所有外部 Channel 的通用行为。
5. 不引入实例级全局“当前会话”状态，继续遵守消息自带会话身份、不同会话可并行处理的现有模型。

本项只记录 CLI 新会话的用户需求和边界，不预设命令归属、会话标识生成方式或其他 Channel 的
会话切换方案。

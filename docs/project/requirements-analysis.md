# NucleaMind 需求分析

- 状态：评审后修订
- 更新时间：2026-08-10
- 文档阶段：整体需求分析
- 适用范围：NucleaMind Kernel、内建默认能力、原生插件体系、官方扩展插件与生态兼容层

## 1. 文档目的

本文档用于明确 NucleaMind 的产品边界和系统需求，作为后续架构设计、接口设计、
迁移计划和测试验收的共同依据。

本阶段只分析“系统需要解决什么问题”，不确定具体包结构、类名、数据库、序列化格式
或第三方框架，也不进行代码实现。

## 2. 背景与问题定义

NucleaMind 基于 nanobot 的现有实现继续开发。nanobot 已具备完整个人 AI 助手能力，
但 Agent Runtime、Memory、Channel、Tools、MCP、Automation、WebUI 和 Multi-Agent
等能力主要位于同一代码库，随着能力增加会产生以下问题：

- 核心职责持续膨胀，改动任一功能都可能影响主执行路径。
- 功能与运行时耦合，用户难以按需安装、替换或组合能力。
- 扩展接口不统一，第三方开发者需要了解大量宿主内部实现。
- 配置、依赖和生命周期缺乏统一的插件级管理边界。
- 难以兼容其他 Agent 的插件生态，也难以形成独立的 NucleaMind 生态。

NucleaMind 需要将现有完整应用逐步重构为稳定的小型 Agent Kernel，并通过插件恢复和
扩展个人 AI 助手能力。

## 3. 产品定位

NucleaMind 是一个面向个人 AI 助手场景的轻量级、模块化 Agent Kernel。

它提供：

- 执行一次或持续多次 Agent turn 所需的最小运行机制。
- 一套内建默认能力，使安装后无需任何插件即可作为可用的基础 Agent 运行。
- 稳定、可版本化的扩展接口和插件生命周期。
- 组合模型、上下文、记忆、工具、渠道和工作流等能力的统一机制。
- 可自托管、可替换、可裁剪的运行环境。
- 原生插件和外部生态兼容插件的承载能力。

“最小核心”指能力范围最小，不指开箱不可用。NucleaMind 应当像 Pi 一样，安装并配置好
模型凭据后即可直接使用，只是默认只具备最基础的 Agent 能力。

它不以“默认集成所有能力”为目标，也不规定唯一的 Memory、Channel、Workflow、
Multi-Agent 或模型供应商实现；内建默认能力只提供基础可用水平，不追求功能深度。

## 4. 目标与非目标

### 4.1 核心目标

1. **最小核心**：Kernel 只保留所有 Agent 必需且无法合理外置的机制，以及维持基础可用
   所必需的内建默认实现。
2. **开箱可用**：完成安装并配置一份模型凭据后，不安装任何插件即可完成一次包含工具
   调用的完整 Agent turn。
3. **能力可插拔**：用户可以独立安装、启用、禁用、替换和组合具体能力；内建默认实现
   同样可被禁用或被插件覆盖。
4. **接口稳定**：插件主要依赖公开 SDK，不依赖 Kernel 内部模块。
5. **渐进迁移**：在改造过程中尽量保持 nanobot 已有可用行为，避免一次性重写。
6. **故障隔离**：单个插件失败不应无条件导致整个 Runtime 不可用。
7. **安全可控**：插件只能获得已声明并被用户允许的资源与能力。
8. **生态扩展**：支持原生插件，并为 OpenClaw 等外部生态预留兼容层。
9. **跨平台运行**：至少维持 Windows 与 Linux 的基础开发和运行能力。

### 4.2 首版非目标

- 不在 Kernel 中内置完整工作流引擎或 Multi-Agent 框架。
- 不在 Kernel 中内建具体聊天平台、浏览器、向量数据库、Automation 或 WebUI。
- 不追求内建默认能力的功能深度，只要求其达到基础可用并可被替换。
- 不要求首版支持无重启热更新插件。
- 不保证首版兼容所有 OpenClaw 插件。
- 不定义插件市场、支付、评分、远程分发平台等商业基础设施。
- 不追求分布式 Runtime、多节点调度或云原生控制平面。
- 不一次性重写 nanobot 的全部功能。
- 不在需求阶段确定最终包名迁移方案。

## 5. 用户与参与角色

| 角色 | 主要诉求 |
| --- | --- |
| Agent 使用者 | 装好即可使用基础助手，按需再装插件扩展；配置清晰、安全可控 |
| Agent 组装者 | 组合模型、记忆、渠道、工具和工作流，构建特定用途的 Agent |
| 插件开发者 | 通过稳定 SDK 注册能力，不需要依赖 Kernel 内部实现 |
| Kernel 维护者 | 保持核心小而稳定，能够演进接口并验证兼容性 |
| 兼容层维护者 | 将外部插件契约映射为 NucleaMind 能力，并明确不支持或降级部分 |
| 运维者 | 启动、停止、诊断和升级实例，观察插件与 Agent 的实际运行状态 |

同一名个人用户可能同时承担使用者、组装者和运维者角色。

## 6. 核心领域对象

| 对象 | 含义 |
| --- | --- |
| Agent Instance | 一组配置、工作区、状态和已启用插件构成的独立 Agent 实例 |
| Turn | 从一条输入消息开始，到最终输出或明确失败为止的一次处理过程 |
| Session | 有顺序的多轮交互上下文及其持久化标识 |
| Message | Channel 与 Kernel 之间交换的统一输入或输出消息 |
| Context | 本次模型调用可见的系统指令、历史、记忆和其他补充信息 |
| Capability | 向运行时注册的可调用或可参与执行的能力，由内建默认实现或插件提供 |
| Capability Registry | 保存能力标识、类型、提供方、优先级和选择结果的注册表 |
| Plugin | 带有清单、配置、入口和生命周期的扩展单元 |
| Builtin Default | Kernel 自带、默认启用、可禁用或被插件覆盖的能力实现 |
| Provider | 某类能力的实现，例如 Model、Memory、Context 或 Channel Provider |
| Tool | 可由模型请求执行、具有明确参数和结果契约的能力 |
| Command | 由用户直接触发、不必进入模型即可处理的输入，例如斜杠命令 |
| Skill | 以文本或声明式资源形式提供的能力，不含可执行代码 |
| Hook | 在生命周期或 turn 特定阶段被调用的扩展点 |
| Runtime Event | Turn、模型调用、工具调用、插件状态等运行过程中的结构化事件 |
| Workspace | Agent 状态或当前项目文件所处的受控文件边界 |

## 7. 系统边界

### 7.1 Kernel 必须负责

- Agent turn 的编排和状态转换。
- LLM 调用与 tool-call 循环的抽象控制。
- 统一消息、Session 和 Runtime Event 的基础契约。
- Context 构建流程及 Context Provider 的协调机制。
- Tool 与其他能力的注册、查找和冲突处理。
- 输入分流：判断一条输入由命令处理还是进入模型 turn。
- Plugin Runtime、插件生命周期和公开 SDK 边界。
- 基础配置加载、校验和插件配置分发。
- 必要的取消、超时、错误传播和日志关联机制。
- 用户主动中断进行中 turn 的机制及中断后的状态语义。
- Kernel 级安全边界和能力注册入口。
- §7.3 定义的内建默认能力集，使实例在无插件时即可使用。

### 7.2 应作为插件提供

- Telegram、Discord、Slack、Email、WebUI 等 Channel。
- 具体 Memory 存储、检索和整合策略。
- Browser、Search、MCP、图像生成等具体工具，以及超出 §7.3 基础集的文件与执行工具。
- §7.3 最小内建实现以外的模型供应商实现和供应商认证流程。
- Automation、Heartbeat、Cron、Workflow 和 Multi-Agent。
- RAG、知识图谱、个性化 Prompt 等 Context 策略。
- 外部插件生态兼容适配器。

### 7.3 内建默认能力（开箱可用基线）

Kernel 自带以下默认实现，使实例在不安装任何插件时即可完成一次真实 Agent turn。
这些实现属于“基础可用”水平，功能深度由插件扩展。

| 能力 | 内建范围 | 替换方式 |
| --- | --- | --- |
| CLI 入口 | 单次执行与交互式会话，支持中断 | 不可禁用；可被 Channel 插件补充，实现可被插件覆盖 |
| Model Provider | 至少一种主流协议的最小适配 | 可被 Model Provider 插件覆盖或新增 |
| Session | 基础持久化会话历史与恢复 | 通过 Session 接口整体替换 |
| Context Provider | 系统指令、会话历史和基础裁剪 | 通过 Context 接口替换或追加 Provider |
| 基础工具集 | 文件读、写、编辑、列目录、内容检索、Shell 执行 | 可整体或按工具禁用，可被同名插件覆盖 |
| 命令处理 | 帮助、配置查看、会话与插件状态等最小命令集 | 插件可注册新命令 |
| 配置与凭据 | 配置文件加载、校验与 Secret 引用 | 不可禁用 |

**关键需求**

- `BAS-001`：默认安装不包含任何插件时，实例必须能够正常启动并完成一次包含工具调用的
  完整 turn，唯一必需的用户输入是模型凭据与模型选择。
- `BAS-002`：内建默认能力必须通过与插件相同的公开 SDK 契约注册；Kernel 主执行路径
  只依赖能力接口，不依赖其内建实现。
- `BAS-003`：除配置与凭据、CLI 入口外，每一项内建默认能力都必须可被显式禁用，或被同类
  插件能力按 §9.3 的选择规则覆盖。
- `BAS-004`：内建默认能力被禁用或覆盖后，Kernel 不得回退到内建实现，也不得因缺少内建
  实现而隐式恢复。唯一例外见 `BAS-010`。
- `BAS-005`：内建默认能力必须遵守与插件相同的 Workspace、进程和 SSRF 边界，不得
  因其位于 Kernel 内部而获得额外特权。
- `BAS-006`：首次运行时，缺少模型凭据必须给出可操作的配置指引，指出配置位置和所需字段，
  但不得输出凭据值。
- `BAS-007`：Memory 不属于内建默认能力；无 Memory 时基础对话必须能正常工作。
- `BAS-008`：内建工具集的范围变更等同于 Kernel 接口变更，必须显式评审，不得随需求增长
  自然扩张。
- `BAS-009`：CLI 入口不可禁用。任何配置组合下，实例都必须保留至少一个可直接交互的本地
  入口，不得出现"未安装 Channel 插件即无法使用"的状态。
- `BAS-010`：插件可以覆盖 CLI 入口的实现（例如替换渲染或交互方式），但覆盖失败或插件
  被禁用时必须回落到内建 CLI 实现，而不是失去入口。此为 `BAS-004` 的唯一例外。

### 7.4 最小可用发行组合

Kernel 单独存在时应可被嵌入和测试。面向用户的最小可用组合即 §7.3 的内建默认能力集，
不要求额外安装插件。

用户可在此基础上：

- 安装 Channel 插件接入聊天平台。
- 安装 Memory 插件获得长期记忆。
- 安装 Tool、Context、Model 插件扩展或替换默认行为。

除明确标记为不可禁用的部分外，上述能力都应允许被替换。

## 8. 核心业务逻辑

### 8.1 实例启动流程

1. 加载基础配置并完成结构校验。
2. 注册未被禁用的内建默认能力。
3. 发现显式安装且允许启用的插件。
4. 读取插件清单，校验 SDK 版本、依赖和配置。
5. 计算插件加载顺序，拒绝缺失依赖和依赖环。
6. 创建插件运行上下文。
7. 依次执行加载、注册和启动生命周期。
8. 按能力选择规则解析插件对内建默认能力的覆盖，并记录最终生效实现。
9. 汇总已注册能力并检查唯一性与必需能力。
10. 启动 Channel 或其他长生命周期服务。
11. 发布实例就绪状态；若关键能力缺失，则以明确错误终止启动。

### 8.2 Agent Turn 主流程

1. Channel 或 CLI 入口将外部输入转换为统一 `InboundMessage`。
2. Kernel 校验消息并确定 Agent Instance、Session 和 Workspace 范围。
3. Kernel 判断输入是否命中已注册命令。命中则由命令处理并直接产生输出，不进入模型
   调用；未命中或命令要求继续时才进入模型 turn。
4. 同一 Session 的 turn 默认串行执行，后续消息排队；配置可改为合并或拒绝，任何策略下
   都禁止无序写入历史。
5. Context 构建器收集系统指令、会话历史、Memory 和其他 Provider 贡献。
6. Context 构建器执行优先级、预算、去重和敏感信息控制。
7. Model Provider 接收标准化请求并返回文本、流式增量或 Tool Call。
8. 若模型请求工具，Kernel 校验工具名称、参数和调用预算后执行。
9. Tool Result 以结构化结果返回模型，循环直至产生最终答案或达到终止条件。
10. Turn 在任意阶段可被用户中断或超时取消；Kernel 在下一个可取消检查点停止推进，
    保存已产生的内容并标记为取消，不得标记为正常完成。
11. Kernel 持久化 turn 结果并发布 Runtime Event。
12. Channel 将统一 `OutboundMessage` 转换为目标平台输出。

### 8.3 插件变更流程

1. 用户安装插件包并在实例配置中启用。
2. Runtime 在下一次启动时校验并加载插件。
3. 插件只能通过 SDK 注册其声明的能力。
4. 插件覆盖内建默认能力时，必须在启动结果中明确可见，不得静默替换。
5. 禁用插件后，Runtime 不再注册其能力，也不再启动其后台服务；若该插件曾覆盖内建默认
   能力，是否恢复内建实现由显式配置决定，不得隐式回退。
6. 卸载前应处理插件拥有的持久化状态，默认不得静默删除用户数据。
7. 插件升级导致配置或状态格式变化时，必须显式迁移或给出可恢复错误。

### 8.4 外部生态兼容流程

1. 兼容层识别外部插件及其协议版本。
2. 将外部 manifest、配置和扩展类型映射为 NucleaMind 契约。
3. 对可支持能力建立适配，对部分支持能力声明降级行为。
4. 对无法安全支持的能力拒绝加载并给出具体原因。
5. 兼容插件仍受 NucleaMind 的安全和生命周期规则约束。

## 9. 关键功能模块

### 9.1 Agent Kernel

**职责**

- 维护 turn 状态机。
- 协调 Context、Model、Tool、Session 和输出。
- 控制最大迭代次数、取消、超时和失败结果。
- 为整个 turn 提供稳定的关联标识。

**关键需求**

- `KER-001`：同一套 turn 流程必须可被 CLI、Web、聊天平台和 API 复用。
- `KER-002`：Kernel 主执行路径不得直接依赖具体 Channel、Memory、数据库或模型供应商；
  内建默认实现只能通过与插件相同的能力接口接入。
- `KER-003`：每个 turn 必须有明确的开始、运行、完成、取消或失败状态。
- `KER-004`：Tool Call 必须经过 schema 校验和调用预算校验。
- `KER-005`：达到模型或工具循环上限时必须正常终止并返回可诊断结果。
- `KER-006`：Kernel 必须支持在进入模型调用前将输入分流到命令处理，并定义命令未匹配、
  命令出错和命令要求继续 turn 的行为。
- `KER-007`：用户必须能够中断进行中的 turn。中断后已产生的输出、已发生的工具副作用和
  会话历史状态必须可判定，不得记录为正常完成。
- `KER-008`：同一 Session 的默认并发策略为串行排队；其他策略必须显式配置，且任何策略都
  不得导致历史乱序或并发写入。
- `KER-009`：迭代次数、工具调用次数、单次工具耗时、结果大小和 turn 总超时必须可配置，
  并具有安全默认值；缺省配置下不得无界执行。
- `KER-010`：turn 关联标识必须贯穿命令处理、模型调用、工具调用、持久化和事件发布。

### 9.2 Plugin Runtime

**职责**

- 插件发现、校验、加载、注册、启动、停止和状态查询。
- 依赖排序、版本兼容、能力冲突和故障隔离。
- 向插件提供受限的 Host API。

**关键需求**

- `PLG-001`：插件必须具有稳定标识、版本、SDK 兼容范围、入口和能力声明。
- `PLG-002`：插件不得通过导入 Kernel 私有模块获得隐式能力。
- `PLG-003`：重复插件 ID、重复独占能力或依赖环必须在启动阶段报错。
- `PLG-004`：插件启动失败时，应记录原因并继续运行不依赖它的能力。
- `PLG-005`：插件停止顺序应与启动依赖顺序相反，并支持异步资源清理。
- `PLG-006`：Runtime 必须可以列出插件状态、版本、已注册能力和失败原因，并标明每项能力
  由内建实现还是插件提供。
- `PLG-007`：Plugin Runtime 缺失或全部插件禁用时，实例仍必须能按 §7.3 启动运行。

### 9.3 Plugin SDK 与 Capability Registry

**职责**

- 定义插件可依赖的公开接口。
- 注册、检索和调用不同类型的能力。
- 隔离 SDK 稳定契约与宿主内部实现。

**关键需求**

- `SDK-001`：首版 SDK 必须支持 Tool、Channel、Model、Memory、Context、Session、
  CLI Entry 和 Lifecycle Hook 等扩展类型；Agent/Workflow 属于 P2 扩展面，应在原生
  插件契约稳定后增加，不要求首版提前冻结其接口。
- `SDK-002`：每个能力必须有唯一标识、提供方（内建或具体插件）、类型和版本信息。
- `SDK-003`：Registry 必须定义重复注册、替换、优先级和默认实现选择规则，其中必须覆盖
  插件覆盖内建默认能力的情形。
- `SDK-004`：公开输入输出必须具有明确类型，不允许将宿主内部对象直接暴露给插件。
- `SDK-005`：SDK 演进必须提供兼容范围判断，不兼容时不得尝试带病加载。
- `SDK-006`：SDK 必须支持不含可执行代码的声明式扩展，至少包括 Skill、斜杠命令和系统
  指令片段；此类扩展同样受信任等级与上下文预算约束。
- `SDK-007`：内建默认能力与插件能力必须使用同一注册接口，Registry 不得为内建实现提供
  额外的私有注册通道。

### 9.4 Message 与 Channel

**职责**

- 将任意外部消息转换为 Kernel 可理解的统一格式。
- 将 Kernel 输出转换为目标平台格式。

**关键需求**

- `MSG-001`：统一消息必须包含来源、会话定位、发送者、内容、时间和可选附件。
- `MSG-002`：平台私有字段只能位于受控扩展元数据中，Kernel 不应依赖其具体结构。
- `MSG-003`：Channel 必须处理平台消息长度、附件限制、回复关联和发送失败。
- `MSG-004`：不可信输入必须在 Channel 边界规范化，不能将原始 SDK 对象传入 Kernel。
- `MSG-005`：流式能力不一致时，Channel 可以降级为分段或最终结果发送。
- `MSG-006`：出站消息必须携带足以定位目标 Channel 与外部会话的信息，不得要求 Channel
  依赖自身缓存的 Session 映射才能投递。
- `MSG-007`：CLI 入口与其他 Channel 使用同一消息契约，不得拥有绕过统一格式的专用路径。

### 9.5 Model Provider

**职责**

- 将标准模型请求转换为具体供应商调用。
- 将文本、推理、流式增量、Tool Call 和用量统一返回 Kernel。

**关键需求**

- `MOD-001`：模型能力差异必须可声明，例如工具调用、图像输入、流式和结构化输出。
- `MOD-002`：认证信息只通过受控配置提供，不得进入日志或普通 Runtime Event。
- `MOD-003`：限流、超时、认证失败和内容过滤必须转换为可分类错误。
- `MOD-004`：Provider 不得决定 Session、Memory 或 Channel 行为。
- `MOD-005`：内建最小 Provider 必须支持完成 §7.3 基线所需的对话与工具调用能力；不具备
  的能力必须显式声明为不支持，而非静默降级。

### 9.6 Context Provider

**职责**

- 为一次 turn 提供系统指令、历史摘要、检索结果、记忆或其他上下文片段。
- 在模型上下文预算内组合和裁剪内容。

**关键需求**

- `CTX-001`：每个上下文片段必须标明来源、优先级、估算大小和可见范围。
- `CTX-002`：Context 组合顺序和冲突规则必须确定且可测试。
- `CTX-003`：超出预算时应按策略裁剪或压缩，不得生成超过模型限制的请求。
- `CTX-004`：插件私有数据只有经显式 `ContextFragment` 才能进入模型上下文。
- `CTX-005`：Context Provider 失败时，应跳过该 Provider 并记录原因。
- `CTX-006`：内建默认 Context Provider 必须在无 Memory、无检索插件的情况下产出可用上下文。

### 9.7 Session

**职责**

- 标识连续对话，保存 turn 历史和必要状态。
- 支持 Context 构建、恢复和压缩。

**关键需求**

- `SES-001`：Session 标识必须在不同 Channel、用户、群组和项目之间避免意外冲突。
- `SES-002`：同一 Session 的写入必须保持顺序和原子性。
- `SES-003`：持久化失败不得伪装成成功完成。
- `SES-004`：Session 数据必须可以独立于具体 Channel 读取和迁移。
- `SES-005`：删除、过期、压缩和分支等操作必须有明确数据保留语义。
- `SES-006`：内建默认 Session 实现必须提供跨进程重启的历史恢复，且其存储格式可被外部
  实现读取或迁移。

### 9.8 Memory Provider

**职责**

- 保存和检索跨 Session 的长期信息。
- 可选地执行整合、遗忘、去重和重要性判断。

**关键需求**

- `MEM-001`：Kernel 只依赖 Memory Interface，不假设文件、向量或图数据库。
- `MEM-002`：写入与检索必须携带 Agent、用户或 Workspace 范围。
- `MEM-003`：Memory 不可用时，基础对话应能按配置降级为无长期记忆模式。
- `MEM-004`：写入模型生成内容前应支持来源和可信度标记。
- `MEM-005`：用户必须能够查询、修正和删除可识别的长期记忆。

### 9.9 Tool System

**职责**

- 向模型公开可调用能力并执行经过校验的请求。

**关键需求**

- `TOL-001`：Tool 必须声明名称、描述、输入 schema 和输出语义。
- `TOL-002`：同一 turn 内必须限制调用次数、持续时间和结果大小。
- `TOL-003`：超大结果应截断、摘要或转为引用，不得无限注入 Context。
- `TOL-004`：有副作用的工具应支持明确的风险等级或确认策略。
- `TOL-005`：文件、Shell 和网络工具不得绕过 Workspace、沙箱和 SSRF 边界。
- `TOL-006`：内建基础工具集必须可按单个工具粒度禁用，且模型可见的工具列表必须与实际
  可执行集合一致。
- `TOL-007`：TOL-002 中的各项上限必须可配置并具有安全默认值。

### 9.10 Config 与 Secret

**职责**

- 管理 Kernel 配置、实例配置和插件配置。
- 提供显式校验、默认值和 Secret 引用。

**关键需求**

- `CFG-001`：未知字段、错误类型和缺失必填项必须产生可定位错误。
- `CFG-002`：插件只能读取自身配置和明确授予的共享配置。
- `CFG-003`：配置保存不得将环境变量解析出的 Secret 回写为明文。
- `CFG-004`：插件配置 schema 应随插件版本进行兼容判断。
- `CFG-005`：测试配置、临时配置和正式配置必须能够分离。

### 9.11 Runtime Event 与可观测性

**职责**

- 以统一事件表示实例、插件、turn、模型和工具的状态变化。

**关键需求**

- `OBS-001`：事件至少包含事件类型、时间、实例 ID 和关联 ID。
- `OBS-002`：事件顺序应足以还原单个 turn 的关键执行过程。
- `OBS-003`：日志和事件默认脱敏，不输出 API Key、Token、完整敏感 Context。
- `OBS-004`：诊断信息应区分用户错误、插件错误、外部服务错误和 Kernel 错误。
- `OBS-005`：可观测接口不得绑定 WebUI 或某个具体 Channel。

### 9.12 生态兼容层

**职责**

- 将外部插件协议适配为 NucleaMind 的公开 SDK 和能力模型。

**关键需求**

- `CMP-001`：兼容范围必须以版本和能力矩阵明确描述。
- `CMP-002`：适配器不得削弱 NucleaMind 的安全检查。
- `CMP-003`：不支持的 API 必须在加载期或调用期返回明确错误，不得静默忽略。
- `CMP-004`：兼容层与原生 Plugin Runtime 解耦，不得成为 Kernel 必需依赖。

### 9.13 命令与声明式扩展

**职责**

- 处理无需模型即可完成的用户输入。
- 承载 Skill、Prompt 片段等不含可执行代码的扩展资源。

**关键需求**

- `CMD-001`：命令必须声明名称、参数形式、说明和操作员限制，并可被 Registry 统一列出。
- `CMD-002`：命令命名冲突必须在启动阶段报错，不得由加载顺序决定生效实现。
- `CMD-003`：命令处理失败不得导致实例退出，必须返回可诊断错误并保持会话可用。
- `CMD-004`：Skill 与 Prompt 片段进入 Context 时，必须遵守 §9.6 的来源、优先级、预算和
  敏感级别规则，不得凭借文本形式绕过限制。
- `CMD-005`：不可信来源的声明式扩展内容不得获得高于系统指令的指令优先级。

### 9.14 安装与发行

**职责**

- 定义主程序与插件的安装、升级和卸载方式。

**关键需求**

- `DST-001`：主程序安装必须一步得到 §7.3 的完整内建默认能力，不要求用户额外安装组件。
- `DST-002`：插件安装、升级、禁用和卸载必须有明确的用户可执行方式，且与实例配置中的
  启用状态解耦。
- `DST-003`：安装和启动不得依赖对外部插件仓库的强制网络访问；离线环境下内建默认能力
  必须可用。
- `DST-004`：插件包必须声明其外部运行时依赖，安装期缺失依赖必须在启用前暴露。
- `DST-005`：同一主机上的多个 Agent Instance 必须具有独立的配置、状态目录和运行时资源，
  并对共享资源冲突给出明确错误。

## 10. 输入输出规范

以下为逻辑规范，具体数据类型和序列化方式留待接口设计阶段确定。表中字段名仅表示逻辑
含义，不代表最终的命名风格或序列化形式。

### 10.1 插件清单输入

| 字段 | 必需 | 说明 |
| --- | --- | --- |
| `id` | 是 | 全局稳定、大小写规则明确的插件标识 |
| `version` | 是 | 插件版本 |
| `sdk_range` | 是 | 支持的 NucleaMind SDK 版本范围 |
| `entrypoint` | 是 | 插件入口 |
| `capabilities` | 是 | 插件声明提供的能力类型和标识 |
| `dependencies` | 否 | 其他插件或 Host 能力依赖 |
| `config_schema` | 否 | 插件配置约束或其引用 |

**输出**：加载成功后的插件状态，或包含插件 ID、失败阶段、错误类别和可操作建议的错误。

### 10.2 统一输入消息

| 字段 | 必需 | 说明 |
| --- | --- | --- |
| `message_id` | 是 | 来源范围内稳定的消息标识 |
| `instance_id` | 是 | 目标 Agent Instance 标识 |
| `channel_id` | 是 | Channel 实例标识，CLI 入口同样适用 |
| `conversation_id` | 是 | 外部对话标识 |
| `sender` | 是 | 规范化发送者信息 |
| `content` | 是 | 文本或结构化内容 |
| `attachments` | 否 | 附件引用、媒体类型、大小和受控访问方式 |
| `reply_to` | 否 | 被回复消息标识 |
| `timestamp` | 是 | 带时区或统一时基的时间 |
| `metadata` | 否 | 有命名空间、大小受限的平台扩展数据 |

**校验规则**

- 标识不得为空，内容和附件至少存在一项。
- 附件不能只依赖未经授权的本地绝对路径。
- 元数据必须限制大小，并在进入 Kernel 前移除不可序列化的 SDK 对象。

### 10.3 统一输出消息

| 字段 | 必需 | 说明 |
| --- | --- | --- |
| `session_id` | 是 | 对应 Session |
| `channel_id` | 是 | 目标 Channel 实例 |
| `conversation_id` | 是 | 目标外部对话 |
| `turn_id` | 是 | 关联的 turn，便于流式与事件对齐 |
| `content` | 是 | 最终文本或结构化内容 |
| `attachments` | 否 | 可交付给 Channel 的附件引用 |
| `reply_to` | 否 | 回复目标 |
| `stream_state` | 否 | 开始、增量、完成、取消或失败 |
| `metadata` | 否 | 不影响 Kernel 逻辑的受控扩展信息 |

输出内容必须允许 Channel 根据平台限制执行分段、格式降级或附件转换。取消和失败状态必须
与正常完成可区分，Channel 不得将其呈现为完整答案。

### 10.4 Context 贡献

| 字段 | 必需 | 说明 |
| --- | --- | --- |
| `source` | 是 | Provider 和数据来源 |
| `content` | 是 | 提供给模型的内容 |
| `priority` | 是 | 冲突和裁剪时的优先级 |
| `estimated_size` | 是 | Token 或可比较的大小估算 |
| `scope` | 是 | Agent、用户、Session 或 Workspace 范围 |
| `sensitivity` | 否 | 敏感级别和传播限制 |
| `expires_at` | 否 | 内容失效时间 |

### 10.5 Tool Call 与 Tool Result

**Tool Call 输入**

- 调用 ID。
- Tool 唯一标识。
- 符合 Tool schema 的参数。
- Turn、Session 和调用方关联信息。
- 超时和幂等相关执行上下文。

**Tool Result 输出**

- 对应调用 ID。
- 成功状态或结构化错误。
- 供模型消费的有界内容。
- 可选机器可读数据和外部产物引用。
- 是否发生副作用、结果是否被截断。
- 执行耗时和安全的诊断信息。

Tool 错误不得伪装为普通成功文本；异常堆栈不得直接暴露给模型或最终用户。

### 10.6 Model 请求与响应

**请求至少包含**

- 模型标识和所需能力。
- 有序消息与 Context。
- 可用 Tool 定义。
- 采样、最大输出和超时等受支持参数。
- Turn 关联 ID。

**响应可能包含**

- 文本或结构化内容。
- 流式增量。
- Tool Call。
- 终止原因。
- Token 或费用用量。
- 经过归一化的 Provider 元数据。

Provider 私有响应对象不得直接越过 Provider 边界。

### 10.7 错误输出

统一错误至少包含：

- 稳定错误代码。
- 错误类别。
- 面向用户的安全说明。
- 面向诊断的脱敏详情。
- 是否可重试。
- 失败的能力标识及其提供方是内建实现还是具体插件。
- Turn/Session/Instance 关联 ID。

错误类别至少应区分：输入无效、配置错误、能力缺失、权限拒绝、依赖不兼容、超时、
取消、外部服务失败、插件失败、持久化失败和 Kernel 内部错误。

## 11. 边界条件与异常场景

本节场景均带编号，便于架构设计和测试用例追溯。

### 11.1 启动与插件

- `EDG-101`：未安装任何插件时，实例必须按 §7.3 正常启动并可用，且 CLI 入口始终可用；
  仅当可禁用的内建默认能力被禁用且无替代实现时，才报告能力缺失。
- `EDG-102`：插件 ID 重复、能力冲突、依赖缺失、依赖环或 SDK 不兼容时不得随机选择实现。
- `EDG-103`：插件在注册了一部分能力后失败时，必须回滚其未完成注册。
- `EDG-104`：插件停止超时不能无限阻塞实例退出。
- `EDG-105`：禁用插件后，其后台任务、事件订阅和能力引用不得继续存活。
- `EDG-106`：外部插件不能声明自身故障足以中断宿主；内建基线装配错误由 Runtime 按宿主
  身份直接拒绝，不由 manifest 字段控制。
- `EDG-107`：覆盖内建默认能力的插件加载失败时，必须按覆盖语义明确处理，不得由加载顺序
  偶然决定；覆盖 CLI 入口的插件失败时按 `BAS-010` 回落到内建 CLI。
- `EDG-108`：配置试图禁用 CLI 入口时，必须显式拒绝该配置并说明原因，不得静默忽略后
  按启用处理。

### 11.2 消息与 Session

- `EDG-201`：重复投递的外部消息需要可识别，避免重复执行高风险副作用。
- `EDG-202`：同一 Session 同时收到多条消息时，必须按 KER-008 的策略排队、合并或明确拒绝，
  不得无序修改历史。
- `EDG-203`：不同用户、群组、Channel 和项目不能因简单拼接标识而错误共享 Session。
- `EDG-204`：Channel 在最终回复前断开时，turn 的执行、取消和结果保存策略必须明确。
- `EDG-205`：空文本、大文本、未知附件、损坏媒体和不支持内容类型必须产生可预期结果。
- `EDG-206`：用户在 turn 进行中重复发送中断信号时，行为必须幂等，不得留下不一致状态。

### 11.3 Context、Memory 与模型

- `EDG-301`：Context 超出模型窗口时必须有确定的裁剪或压缩策略。
- `EDG-302`：Memory 或某个 Context Provider 超时不能无限阻塞 turn。
- `EDG-303`：模型返回未知 Tool、无效参数、重复 Tool Call 或空响应时必须受控终止或重试。
- `EDG-304`：流式响应中途失败时，不得将部分输出错误地标记为完整答案。
- `EDG-305`：切换 Model Provider 后，历史中的供应商私有结构必须可降级或规范化。
- `EDG-306`：Memory 中存在冲突、过期或恶意内容时，必须保留来源并限制其指令优先级。
- `EDG-307`：未安装 Memory 插件时，Context 构建必须正常完成，不得产生缺失依赖错误。

### 11.4 Tool 与副作用

- `EDG-401`：Tool 超时、取消或进程崩溃后，必须明确副作用是否可能已经发生。
- `EDG-402`：网络重试可能导致重复提交时，需要幂等键或禁止自动重试。
- `EDG-403`：Tool Result、附件和日志过大时必须限制大小。
- `EDG-404`：Shell、文件和网络工具必须处理 Windows 与 Linux 的路径和命令差异。
- `EDG-405`：路径符号链接、`..`、大小写差异和重解析点不能绕过 Workspace 边界。
- `EDG-406`：URL 重定向、DNS 解析变化和代理配置不能绕过 SSRF 策略。
- `EDG-407`：turn 被中断时，正在执行的工具必须收到取消信号；无法取消的工具必须在结果中
  标记其副作用状态未知。

### 11.5 配置、升级与数据

- `EDG-501`：配置文件缺失、损坏或包含未知版本时，不得静默回退后覆盖原文件。
- `EDG-502`：Secret 环境变量缺失时，应指出变量名，但不得输出其值。
- `EDG-503`：插件升级失败时，应尽量保留旧配置和状态，并提供回滚路径。
- `EDG-504`：Session 和 Memory 写入必须防止进程崩溃造成半写文件。
- `EDG-505`：卸载插件不得默认删除其数据；数据清理必须是显式操作。
- `EDG-506`：首次运行且无配置文件时，必须生成可用的最小配置或给出明确的初始化指引，
  不得以内部错误终止。
- `EDG-507`：同一主机多个实例同时启动时，配置目录、状态目录和端口占用冲突必须显式报错。

## 12. 非功能需求

本节需求同样带编号，作为架构评审的约束项。

### 12.1 模块化与可维护性

- `NFR-101`：Kernel 主执行路径不得导入任何具体能力实现，内建默认实现必须位于独立模块
  并只通过能力接口接入。
- `NFR-102`：Kernel 不得导入任何独立发布的官方插件包。
- `NFR-103`：插件只依赖公开 SDK；私有 API 不提供兼容承诺。
- `NFR-104`：核心接口数量应受控，新增接口必须证明无法通过现有机制实现。
- `NFR-105`：允许边缘实现存在适量重复，避免为统一所有插件引入复杂继承体系。
- `NFR-106`：内建默认实现必须能够在不修改 Kernel 主执行路径的前提下被移除或替换。

### 12.2 可靠性

- `NFR-201`：Turn、Session 和插件生命周期必须有明确状态机。
- `NFR-202`：关键持久化操作需要原子写或等价事务保证。
- `NFR-203`：失败必须可分类、可关联、可恢复或明确不可恢复。
- `NFR-204`：默认不因非关键观察者、UI 或遥测插件故障中断 Agent turn。
- `NFR-205`：内建默认能力失败必须与插件失败使用同一套错误分类和上报路径。

### 12.3 安全

- `NFR-301`：插件是受信任的同进程代码；安装并启用即完全信任，不提供虚假的应用级授权。
- `NFR-302`：宿主文件服务必须遵守 Workspace 边界。
- `NFR-303`：网络访问默认执行 SSRF 防护。
- `NFR-304`：Shell 默认受 Workspace 限制，并可使用更强的进程级沙箱。
- `NFR-305`：Secret 不进入普通日志、消息历史、模型 Context 或插件间广播事件。
- `NFR-306`：外部插件和内建能力使用相同的公开资源服务，不得获得私有宿主通道。

### 12.4 性能

- `NFR-401`：未使用的插件不得显著增加启动时间和常驻资源。
- `NFR-402`：Context Provider、Hook 和事件订阅应支持异步执行，但必须受超时约束。
- `NFR-403`：插件发现与能力查询不应在每次 Tool Call 时重复进行昂贵扫描。
- `NFR-404`：大型 Tool Result、历史和 Memory 必须有容量边界。
- `NFR-405`：无插件的默认安装启动开销必须显著低于加载完整插件集，且交互式入口的启动
  延迟需在架构阶段设定可测量目标。

首版不预设绝对性能指标；架构设计阶段应基于 nanobot 基线建立可测量指标。

### 12.5 可观测性

- `NFR-501`：每个实例、turn、模型调用和工具调用应具有可关联标识。
- `NFR-502`：支持查询当前已加载插件、能力注册情况和失败状态，且能区分内建实现与插件
  实现，并显示被覆盖的能力。
- `NFR-503`：日志应包含足够诊断信息，同时默认脱敏。
- `NFR-504`：Runtime Event 应可被 CLI、WebUI 或独立观察插件消费。

### 12.6 可移植性

- `NFR-601`：支持 Python 3.11 及项目最终确定的后续版本范围。
- `NFR-602`：保持 Windows 和 Linux 基础运行能力。
- `NFR-603`：路径处理使用平台无关语义，Shell 命令明确区分执行环境。
- `NFR-604`：插件包应声明平台和外部依赖限制。
- `NFR-605`：内建基础工具集必须在 Windows 和 Linux 上具有一致的对外行为契约。

### 12.7 可测试性

- `NFR-701`：Kernel 可使用内存型或模拟 Provider 独立测试，且可在禁用全部内建默认实现的
  情况下运行。
- `NFR-702`：每种插件能力应有契约测试，内建默认实现必须通过同一套契约测试。
- `NFR-703`：官方插件需要验证启用、禁用、配置错误、生命周期和主要业务路径。
- `NFR-704`：兼容层需要按外部生态版本维护能力矩阵和回归样例。
- `NFR-705`：必须存在覆盖“全新安装到完成一次带工具调用 turn”的端到端测试。

## 13. 潜在技术难点

### 13.1 从现有单体中抽取稳定边界

当前实现中的 AgentLoop、Context、Session、Memory、Channel 和 WebUI 存在真实调用关系。
最大的风险是仅移动文件而没有消除所有权耦合，或为追求纯粹架构导致一次性重写。

### 13.2 插件能力模型的粒度

接口过粗会迫使插件依赖宿主内部对象，接口过细会形成大量生命周期和事件组合。
需要在“可替换能力”与“稳定的最小 Host API”之间取得平衡。

### 13.3 生命周期、依赖与异步资源

Channel、后台任务、数据库连接和 MCP 服务都具有异步启动与停止行为。依赖排序、
部分失败回滚、取消传播和关闭超时需要统一语义。

### 13.4 Session、Context 与 Memory 的职责划分

三者都可能接触对话历史，但数据所有权、保留周期、压缩责任和检索策略不同。
边界不清会导致重复持久化、Context 污染和插件间状态不一致。

### 13.5 配置与插件包演进

插件版本、SDK 版本、配置 schema 和持久化状态需要独立演进。必须避免自动迁移失败后
覆盖用户配置，也要避免 Kernel 为每个插件维护专有迁移逻辑。

### 13.6 动态插件与静态类型

插件天然是动态加载边界，但 Kernel 内部需要清晰类型。manifest、外部 payload 和
插件返回值应在边界一次校验，不能让 `Any` 或第三方 SDK 对象向核心扩散。

### 13.7 插件信任与 Python 进程隔离

同进程 Python 插件无法仅依赖类型接口实现真正安全隔离。安装并启用插件即完全信任其代码；
需要运行不可信代码时使用独立进程、容器或操作系统策略，不在 Kernel 内模拟权限沙箱。

### 13.8 OpenClaw 兼容

外部插件可能依赖 OpenClaw 的宿主服务、配置模型、事件语义和隐式全局状态。
兼容工作不能只做函数名映射，需要能力矩阵、适配上下文和明确降级策略。

### 13.9 渐进迁移期间的双重机制

旧内建能力与新插件机制可能在一段时间内并存。需要防止重复注册、配置来源冲突和
行为漂移，并为每个迁移模块定义唯一切换点和回退路径。

### 13.10 内建默认能力与最小核心的张力

内建默认实现是开箱可用的前提，但也是核心膨胀最可能的入口。风险有两个方向：一是内建
实现逐步获得插件拿不到的内部访问，使 SDK 失去真实约束；二是内建工具和默认 Provider
随需求不断增补，最终变回单体。

需要在架构阶段固定两条机制：内建实现只能使用公开 SDK 契约注册和运行；内建能力集的
范围变更走与接口变更相同的评审流程（BAS-002、BAS-008、NFR-101、NFR-702）。

### 13.11 命令、Skill 与模型指令的优先级

命令分流、Skill 文本和系统指令都会影响模型行为，但来源可信度不同。需要明确哪些内容
可以约束模型、哪些只能作为数据，避免不可信扩展通过文本获得高于系统指令的效力
（CMD-004、CMD-005、EDG-306）。

## 14. 迁移需求与阶段边界

阶段与 §15 优先级的对应关系：阶段一至阶段二覆盖 P0，阶段三覆盖 P1，阶段四覆盖 P2。

### 阶段一：基线与 Kernel 边界（P0）

- 固化 nanobot 现有关键行为和测试基线。
- 明确 Kernel 最小职责、领域契约和依赖方向。
- 确定 §7.3 内建默认能力的范围，并从 nanobot 现有实现中裁剪出该基线。
- 不迁移大量功能。

### 阶段二：Plugin Runtime 最小闭环（P0）

- 实现 manifest、生命周期、Registry 和最小 SDK。
- 将内建默认能力改为经由公开 SDK 注册，使 SDK 在首版即被自身使用。
- 选择一个低风险能力完成从内建到插件的端到端验证，并验证其对内建实现的覆盖。
- 验证安装、启用、禁用、错误诊断和测试方式。

### 阶段三：官方能力逐步插件化（P1）

- 按依赖和风险迁移 Channel、Tool、Memory、Context、Model 等能力。
- 每迁移一个模块，都要保持或明确调整现有用户行为。
- 迁移过程中不得削弱 §7.3 的开箱可用基线。
- 旧路径只在迁移窗口内保留。

### 阶段四：生态兼容（P2）

- 在原生插件契约稳定后实现 OpenClaw Adapter。
- 先支持最小官方插件样例，再逐步扩展能力矩阵。
- 兼容层不反向污染 Kernel 接口。

## 15. 首版优先级

### P0：必须完成

- Kernel 职责和公开数据契约。
- §7.3 内建默认能力集：CLI 入口、最小 Model Provider、Session、Context、基础工具集、
  最小命令集、配置与凭据加载。
- 无插件默认安装的开箱可用与首次运行体验（BAS-001、BAS-006、EDG-506）。
- Plugin Runtime 最小生命周期。
- Capability Registry、冲突规则与内建能力覆盖规则。
- Tool、Context、Model 和 Channel 的最小扩展接口。
- 命令分流与 turn 中断机制。
- 插件配置校验、错误分类和状态查询。
- 至少一个端到端示例插件，且需覆盖一次对内建能力的覆盖。
- Workspace、Secret、网络和 Tool 资源边界。
- 渐进迁移与回归验证机制。

### P1：应当完成

- Memory Provider 接口和基础 Memory 插件。
- Session 与 Context 内建实现的可替换验证。
- Runtime Event 订阅接口。
- 官方 Channel、扩展 Tool 和额外 Model Provider 插件化。
- Skill 与声明式扩展的完整支持。
- 插件安装、依赖和配置迁移机制。

### P2：后续扩展

- OpenClaw 插件兼容层。
- Workflow、Automation 和 Multi-Agent 插件。
- 插件热加载或进程隔离。
- 插件市场和远程分发。

## 16. 验收标准

整体需求进入架构设计阶段前，应满足：

1. 能清晰回答哪些职责属于 Kernel 机制、哪些属于内建默认能力、哪些必须位于插件。
2. 能描述从实例启动到完成一次 Agent turn 的完整业务流程，包含命令分流与中断路径。
3. 每类核心输入输出都有明确的逻辑字段、校验和错误语义。
4. 关键异常场景具有确定的失败或降级原则，且带编号可追溯。
5. 首版范围与长期愿景已经分离，不要求一次完成全部插件化。
6. 安全、可靠性、跨平台和可观测性被视为功能约束，而非后期补充。
7. 后续每个架构设计和开发任务都能追溯到本文档中的编号需求。

### 16.1 开箱可用里程碑

- 全新环境完成安装后，只配置模型凭据即可完成一次包含工具调用的 turn。
- 未安装任何插件时，`列出能力`类查询能够展示全部内建默认能力及其提供方。
- 缺少模型凭据时，得到指向配置位置和字段名的可操作错误，且不泄露凭据值。
- 交互式入口可中断进行中的 turn，中断后会话仍可继续使用。
- 在未安装任何 Channel 插件、且尝试禁用全部可禁用内建能力的配置下，CLI 入口仍然可用。

### 16.2 首个 Plugin Runtime 里程碑

- Kernel 可以在不修改主循环的情况下加载一个外部插件。
- 插件可以通过 SDK 注册一种能力并参与真实 Agent turn。
- 插件可以覆盖一项内建默认能力，且启动结果中能看出最终生效实现。
- 插件禁用后该能力不再存在，恢复内建实现与否由显式配置决定。
- 插件配置错误、版本不兼容和运行失败都有稳定、可诊断的结果。
- 官方示例插件不导入 Kernel 私有模块。
- 内建默认实现与同类插件通过同一套契约测试。
- 原有对应能力的关键行为具有回归测试或明确迁移说明。

## 17. 决策记录与设计决策项

### 17.1 已确认

| 问题 | 结论 |
| --- | --- |
| Session 存储归属 | Kernel 内建默认实现，通过 Session 接口可整体替换 |
| Context 构建归属 | Kernel 内建默认 Provider，可替换或追加 |
| 基础 CLI 归属 | Kernel 自带入口，不可禁用，实现可被插件覆盖但失败时回落 |
| Model Provider 归属 | Kernel 保留一个最小协议适配实现，其余通过插件提供 |
| 基础工具集归属 | 文件读写编辑、列目录、检索、Shell 内建，其余工具走插件 |
| Memory 归属 | 不内建，作为可选插件；无 Memory 时基础对话可用 |
| 开箱可用范围 | 仅需模型凭据即可完成一次带工具调用的 turn |

### 17.2 设计阶段决策项

以下问题在需求分析阶段不预设答案，已在
[`technical-design.md` §15](./technical-design.md#15-172-设计决策项的结论)
逐项给出结论、依据和验证方法：

1. Plugin Runtime 首版采用 Python entry point、显式路径、包清单还是组合发现方式。
2. 插件信任采用同进程完全信任；进程隔离属于外部部署能力。
3. Capability 是允许多个实现并由配置选择，还是部分类型只允许单一实现；内建实现在优先级
   中的默认位置如何确定。
4. 内建默认能力是与 Kernel 同包发布，还是同仓库独立子包发布。
5. 内建最小 Model Provider 选择哪一种协议作为默认。
6. Hook/Event 的同步顺序、错误传播和并发策略。
7. turn 中断的可取消检查点粒度，以及不可取消工具的处理方式。
8. 插件持久化状态的目录所有权、备份、迁移和卸载语义。
9. 多实例的配置与状态目录布局，以及实例间资源冲突的检测方式。
10. 原生插件 SDK 的版本策略和兼容承诺周期。
11. 内建能力集范围变更的评审门槛与判定标准。
12. OpenClaw 首批兼容的插件类型和明确不支持的宿主 API。

需求变化导致其中任一结论失效时，必须同时修订需求、技术方案与开发计划。
